# Execution

Step 4 of this skill, for a candidate the user has asked in so many words to implement. Uses the vocabulary in LANGUAGE.md. The structure changes; the behaviour does not. If the work turns up a missing feature or a real bug, note it and leave it for after the structural change, which is checked against today's behaviour.

1. **Pin current behaviour first.** Before any structure moves, write a characterization test through the interface today's callers use, covering what the change will touch: the results callers read, the errors they branch on, the side effects. Type check and lint are not a pin. It records what the code does now, so take the expected values from today's behaviour, run it in the project's own test runner (pytest or unittest, `go test`, `cargo test`, JUnit, RSpec, the package's test script), see it pass on today's code, and commit it. Where a unit test cannot reach, record a baseline instead: outputs for fixed inputs, diffed after every step.
2. **Prove the pin can fail.** Use the two-edit check from `tdd` if it is installed, or the harness of `mutation-test` if that is installed. Without them, break the behaviour by hand in the code the change will touch (return a wrong value, skip an effect), run the pin, watch it fail, then restore with `git checkout -- <file>` and confirm `git status` is clean. A pin that still passes proves nothing: tighten it first. Do not run a red-green loop on the pin; it passes at once by design, and that loop throws such a test away.
3. **Move in small steps, each on green.** Follow the "refactor only on green" rule of `tdd` if it is installed; without it, run the pin and the existing tests after every step, undo a step that turns one red instead of fixing forward, and commit each green step. Make the edits in this session, not through subagents.
4. **Migrate every caller and delete the old path in one wave** when every caller is in this repository: no compatibility shim, no old and new paths side by side. Search for the old names in code, strings, configuration, docs and tests, not only in imports. Delete tests that only guarded the old internals; keep the pin. For a published library or a public API with callers outside this repository, say so, stop once the new path is in, and leave the deprecation path to the user.
5. **Check the result.** Run the whole test suite, then the reader-load test again on the area. If neither layers nor state went down, say so and offer to revert. Report the structure that changed, the pin and how you proved it can fail, the callers moved and what was deleted.
