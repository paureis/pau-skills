# Execution

Step 4 of this skill, for a candidate that the user, or the brief you are working from, has asked in so many words to implement. Uses the vocabulary in LANGUAGE.md. The structure changes; the behaviour does not. If the work turns up a missing feature or a real bug, note it and leave it for after the structural change, which is checked against today's behaviour.

**Before the first edit.** List every decision the grilling loop left open, with the default you will use for each, and go ahead only on the user's yes to that list (or the brief's). Run `git status`: if it shows uncommitted work, ask the user to commit or stash it, or work in a separate worktree, and do not start until the tree is clean. If you are on the default branch, create a branch for this change. From here on, touch only what execution changed: stage files by name (never `git add -A` or `git commit -a`), and undo by restoring files from your own last commit on this branch.

1. **Pin current behaviour first.** Before any structure moves, write a characterization test through the nearest interface above the change that the change leaves in place (a function or module the change deletes cannot hold the pin), covering what the change will touch: the results callers read, the errors they branch on, the side effects. Type check and lint are not a pin. It records what the code does now, so take the expected values from today's behaviour, run it in the project's own test runner (pytest or unittest, `go test`, `cargo test`, JUnit, RSpec, the package's test script), see it pass on today's code, and commit it. Where a unit test cannot reach, record a baseline instead: outputs for fixed inputs, diffed after every step.
2. **Prove the pin can fail.** With the pin committed, break the behaviour once in each place the change will touch (return a wrong value, skip an effect, drop a check) and run only the pin (`pytest -k`, `go test -run`, `cargo test <name>`, or its single test file), so an older test cannot be the one that catches the break. Use the two-edit check from `tdd` if it is installed, or the harness of `mutation-test` if that is installed. Without them, make each break by hand, watch the pin fail, restore the file with `git checkout HEAD -- <file>`, and check that `git status` shows what it showed before the break. A break the pin survives means the pin is too loose: tighten it and break again. Do not run a red-green loop on the pin; it passes at once by design, and that loop throws such a test away.
3. **Move in small steps, each on green.** Follow the "refactor only on green" rule of `tdd` if it is installed; without it, run the pin and the existing tests after every step, and when a step turns a test red, restore the files it changed and take a smaller step. The exception is an existing test that reaches into internals the change removes and goes red while the pin stays green: move what it checks that the pin lacks onto the surviving interface, then delete it in the same step. Commit each green step. A `CONTEXT.md` term settled in the grilling loop was written there; one that first appears now goes in its own commit. Make the edits in this session, not through subagents.
4. **Migrate every caller and delete the old path in one wave.** One wave means within this change, on its branch, possibly over several green commits: no compatibility shim, and no old path survives the change. Search for the old names in code, strings, configuration, docs and tests, not only in imports. Some callers this cannot reach: an interface with callers outside this repository (a published library), a name stored in data (a serialized class name, a type column), a job queued by name, a format an older version still reads during a rolling deploy. For those, say so, stop once the new path is in, and leave the transition to the user.
5. **Check the result.** Run the whole test suite, then the reader-load test again on each question you asked in Explore, and give the before and after counts of layers to trace and state to hold. If reader load did not go down somewhere by more than it went up elsewhere, say so and offer to revert this branch's commits. Report the structure that changed, the pin and how you proved it can fail, the callers moved and what was deleted.
