# Q44 CI says when the roster lock base check found no base

[Back to the backlog index](../BACKLOG.md)

**Q44 CI says when the roster lock base check found no base** (`done` 2026-11-27, pull request 110; found 2026-11-27 in the Q43 plan check
and review). In CI, `ROSTER_LOCK_BASE` is always set, but any no-base outcome passes with a note in the Tests log that
nobody reads. A change that sets `fetch-depth` back to 1, a git timeout, or a force push to main that leaves
`github.event.before` unfetched turns the check off with CI still green.

The owner chose option 1 on 2026-11-27 (the orchestrator's recommendation): CI is the only place that sets the
variable, so a failure there means the guard is off, and a warning can be ignored.

1. Fail when `ROSTER_LOCK_BASE` is set and does not give a base, and keep passing with a note when it is unset (a
   local run). This changes Q43's rule for CI only; a force push to main would then fail its push run.
2. Keep passing, and make the skip visible: a GitHub Actions `::warning::` line from the test, so the run summary
   shows it.

Done when the chosen behaviour is proved with `mutate.sh` and the current tree passes in CI with the base found.

Built in the twenty-ninth batch in `tests/geppetto-roster-lock-base.test.mjs`. With `ROSTER_LOCK_BASE` set and not
empty and no base (a value that starts with "-" or does not resolve, no lock file or no valid `LOCK` at the base, git
cannot run or timed out) the check fails, naming the value, the reason and the fix (keep `fetch-depth: 0`). Unset or
empty, it passes with the same note as before. Four old tests changed on purpose from a pass to a failure; the CI
comments say fetch-depth 0 must stay. Accepted costs, named in the file header: a pull request into a branch older
than the lock file fails, a change that moves the lock file or changes `LOCK`'s format fails its own runs, and a force
push or a push that creates main fails its push run. In pull request 110 all four test jobs named base `HEAD^1` at
main.
