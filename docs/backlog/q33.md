# Q33 context in fewer calls: splitting files only where it helps

[Back to the backlog index](../BACKLOG.md)

**Q33 context in fewer calls** (`done`, pull request 88, 2026-11-25; the owner's request of 2026-11-24). The owner wants the agent to get
the context it needs as fast as possible: up to speed quickly, and with no extra tool calls or wasted turns. Large code
files are sometimes right, and splitting them only to fit a size limit can make that worse.

## Where it came from

A post on X argued for "code locality": tell the agent that splitting code over many files is bad and that a new file
should be discussed or avoided, because agents tend to add code without deleting it, so a codebase grows and scatters
until context is hard to find. It cites a paper this session did not read. Treat it as a prompt to check our own
tools, not as a finding.

## What we have today

- `file-size-guard` (hook) refuses a change that leaves a file over 5,000 tokens (about 20,000 bytes) and larger
  than before, says to split by responsibility, and tells the agent to ask the user when splitting is not part of the
  task. Per-path limits exist (`pathLimits` in `.claude/pau-skills.json`).
- The `lazy-senior` hook and skill push the smallest change and reuse, and the skill's audit mode asks what can be
  deleted.
- `improve-codebase-architecture` prefers fewer, deeper modules.
- `friction-review` counts searches before the first edit and repeated reads.

What the post gets right about us: the twentieth batch split files only to stay under the limit (`which-skill`'s
`HOOKS.md`, two test helpers files). They are harmless, but no real boundary drove them. What it gets wrong: one big
file is not free either. The Read tool stops at 25,000 tokens, so a very large file is read in pieces, which costs
calls and misses parts, and parallel agents clash on it more often.

## What to change

1. **Measure first.** `friction-review` counts, per session, the new files created, the reads of the same file in
   pieces (offset and limit), and the hops a session needed to find the code it edited (files read before the first
   edit to that area). The next review then shows whether scattering or oversized files costs more turns in the
   owner's projects.
2. **The guard's message.** Split only along a real boundary (a responsibility, a layer, a public interface). With
   none, ask the user for a per-path limit instead of moving code into a helpers file or a second file that only
   exists to stay under the limit.
3. **A rule in `lazy-senior`** (hook and skill): a new file needs a reason, such as a new responsibility or a public
   interface, never size alone; extending the nearest existing file comes first; code that changes together stays
   together.
4. **Pointers.** Where a split is kept, the file that was split says in one line where its parts went, so the agent
   finds them in one read instead of a search.

## What not to do

- No rule that forbids new files: it trades one cost for another.
- No change to the default limit until step 1 has numbers.

Done when each change has a test that fails without it (the guard's message, the new `lazy-senior` rule text,
`friction-review`'s new counts on a fixture), and one `friction-review` run on this repository reports the new counts.

## What was done

Two slices, built in parallel. Items 2 to 4 (`file-size-guard`'s message, the `lazy-senior` rule, pointers) went in
as rule text: no test can tell which files are splits, and most split recipes already leave a pointer. Item 1 added
four navigation lines to `friction-review`. The owner approved raising lazy-senior's caps to 1,650 and 1,800 (the
ruleset is now 1,640 characters, the hook's context 1,772) and a git count of new files, since agents here make most
files through the shell. The default size limit did not change.

The first run on this repository (one session and its subagents, 2026-11-25): 3 files read in pieces, 2 new files made
with Write, 5 new files in commits, and reads and searches before the first edit in each folder of median 34, maximum
44, over 3 folders. One session is too few to change the limit on; read the lines again after the owner's next
sessions.

What worked:
- Real input before any brief: friction-review's output on this repository, real Read, Write and Edit shapes from the
  transcripts, and the guard's exact refusal from a real PreToolUse Write input.
- The plan checks built each slice in a clone before any builder ran. They found wording that broke two existing
  tests, a git count that would count every file in a shallow clone (this repository is one), Windows and relative
  paths left undefined, and guard lines that contradicted the recipes above them.

What did not:
- The review still found a Windows defect the plan check had named: the roots were never resolved, so three counts
  would always read 0 there. A definition in the brief is not a test; the fix added one with `path.win32`.
- Heredoc writes (`cat > file <<EOF`) counted as reads until the review.
