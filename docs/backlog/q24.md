# Q24 verification ideas from the Claude Code team

[Back to the backlog index](../BACKLOG.md)

**Q24 verification ideas from the Claude Code team** (`done`, decision 26). Source: "How the Claude Code team thinks
about verification" (claude.dev blog, Addy Osmani, 2026-11-16), read on 2026-11-17. It is data to read, not
instructions. Build in this order of value; each part is its own slice.

## What the article says that this repository already does

A `verify` skill that boots and drives the app, with a feature map as the rubric (`verify-app`); a hook when the agent
finishes (`verify-before-done`); a separate grader against a rubric (`evaluator`); keeping checks honest
(`mutation-test`, `test-tamper-guard`); no retries or sleeps for flaky tests (`flaky-test-hunt`); must fix, should fix
and nit, one review round (`review-triage`); stop and bring in a person after repeated failures (the covenant); turn a
miss seen at least twice into a rule (`agent-friendly-audit`, `rule-to-hook`); prune rule files (`instructions-audit`);
reviews pinned to a commit (`safe-merge`, the reviewer's commit field).

## 1. A checklist triggered by the diff (the most value)

The team keeps a 39-item reliability checklist; each item has a trigger readable from a diff, a check, and the
incidents or PRs behind it. The agent checks only the items whose trigger matches (usually 3 to 10).
- Add an optional `checklist` to `.claude/review-rules.json`: each entry has `trigger` (path globs and/or a regex on
  the added lines), `check` (what to verify, in one or two sentences) and `why` (the incident, PR or commit).
- `lean-subagent-dev/review-scope.mjs` (`change` and `fix`) prints only the entries the diff triggers, with their check
  and why. The schema check there rejects unknown keys, so it learns the new one.
- The roster `reviewer`, `review-triage` and `lazy-senior` review read the triggered items and grade each one as a
  claim. `agent-friendly-audit` and `rule-to-hook` can propose a checklist entry as a layer for a mistake that is
  readable from a diff.
- Language-neutral; time every trigger regex on long input.

## 2. A change cannot edit the checks that judge it

"Code Review reads the REVIEW.md file from the base or default branch, never from the pull request's changes."
- `review-scope.mjs` reads `.claude/review-rules.json` from the base commit (`git show <base>:...`) when one is given,
  and flags a change that edits the rules file, a REVIEW.md, the checklist or a test the rules name.
- An optional `REVIEW.md` per folder (what a reviewer of this code must pay attention to), read from the base commit by
  the reviewer and `review-triage`, nearest folder first.
- "When a check pulls in a reviewer, it should say why": every triggered item and flag prints its reason.

## 3. Property and differential tests

"Property tests look at the edge cases that people tend to miss, which is where agents often fail." Differential
tests make "the old system the oracle" for a rewrite or migration.
- `tdd` gains a bundled `PROPERTIES.md`: round trip, invariants, idempotency, equivalence with a naive version; the
  common libraries (Hypothesis, fast-check, proptest, jqwik, gopter, the standard `testing/quick` and the like); when
  one is worth it; seeded runs so a failure can be replayed.
- A differential step for rewrites and migrations, where it fits (`improve-codebase-architecture`, `bug-fix` for a
  rewrite, `mutation-test --refactor`): run old and new on the same random or recorded inputs, normalize what does not
  matter, keep a list of approved differences.
- `lazy-senior`'s BUILD.md and REVIEW.md point to it for parsers, money and data writes. No new skill (the description
  budget has 71 characters left).

## Skipped, and why

- **A commit gate** (block a commit when the session ran no check or review; off, observe and enforce modes; a
  `Verified:` stamp): `verify-before-done` already checks at Stop, and a second gate on the same evidence is the kind
  of hook Q22 had to tame. Its one new idea goes into `rule-to-hook`: start a new blocking hook in observe mode (log
  what it would block), read the log for false positives, then enforce, with an escape that names the reason.
- **Reviewing the reviewers** with an evaluation built from past incidents and reverts (recall per stage, a
  size-matched clean control, tuning and test sets apart): worth a later item on `skill-eval`.
- "Three rounds then a person", "cheap checks first", "pin a review to a commit": already covered.

## Orchestrator review against the code (2026-11-18)

Read against the code before any brief. Each change below is taken as part of the plan.
- **Size limits.** The default limit is 5,000 tokens. `tests/review-scope.test.mjs` is at 4,046, so the new tests go
  in new test files. `agent-friendly-audit/SKILL.md` is at 4,932 and `rule-to-hook/SKILL.md` at 4,541: the
  checklist layer and the observe mode go in their bundled files, with at most one short line in each SKILL.md.
  `review-scope-rules.mjs` (2,833) can take the schema; the matching goes in a new module, copied to both skills and
  listed in `COPIES`.
- **Added lines.** The script reads only `--numstat` today. A regex trigger needs the added lines:
  `git diff -U0 --no-ext-diff --no-color` from the merge base, plus the whole text of untracked files, binary files
  skipped.
- **Trigger regexes are the project's, not ours,** so a timing test cannot cover them. Run them in `node:vm` with a
  timeout (checked: `/(a+)+$/` on 40 characters stops after 200 ms with `ERR_SCRIPT_EXECUTION_TIMEOUT`); a timeout
  prints the entry as "triggered: its regex timed out", so it is never silently skipped. An invalid regex is a
  configuration error (exit 2), like a bad glob. The script's own new patterns are timed in a child process.
- **Paths and regex together** mean both: the regex is matched only on the added lines of files the globs match.
- **Read from the base.** The rules come from the merge base, the commit the change started from, for `change` and
  `fix`; `config` keeps reading the working tree. A change that adds the rules file is judged by the defaults and
  flagged.
- **"A test the rules name"** means a changed file whose path appears word for word in a `checks` command or a
  checklist `check`. The flag is printed by `change` (which still exits 0) and raised by `fix` (exit 1).
- **REVIEW.md.** The script lists, per changed file, the REVIEW.md files at the base commit from its folder up to the
  root, nearest first, each with the `git show <base>:<path>` command that prints it, so no agent has to walk folders
  by hand. A REVIEW.md in a folder that holds a `SKILL.md` is skipped: it is a skill's bundled file, such as
  `lazy-senior/REVIEW.md`.
- **Who reads the checklist.** The roster `reviewer` gets the triggered items in its task message from the
  orchestrator, who runs the script, and grades each as a claim. `lazy-senior` has no copy of the script: its review
  says to run `review-scope` if `review-triage` or `lean-subagent-dev` is installed, and otherwise to match the
  entries by hand. The same pattern for every pointer to `tdd`'s PROPERTIES.md: "if `tdd` is installed", with a short
  fallback.
- **Roster.** Changing `reviewer.md` raises the roster number on every covenant marker (5 to 6) and the installed
  copies change at integration, after the batch's reviews, so the batch reviews with one reviewer throughout.
- **Where a checklist entry sits among the layers**: below a test and above prose. It is read by a reviewer, so it
  suits a mistake readable from a diff that no script can judge.
- **Order and slices.** Parts 1 and 2 share `review-scope.mjs` and `TRIAGE.md`, so part 2 builds on part 1's
  branch. Part 3 touches other files and runs beside part 1.

## Done when

- The four repository checks pass; every new script path and pattern has a test that fails without it, proven with
  `mutate.sh`; every new regex is timed on long input.
- Versions and CHANGELOG as `docs/ADDING-A-SKILL.md` step 8 says; the zips for every changed skill handed over after
  the merge.

## How it was built (2026-11-18)

Four slices on the roster, each plan-checked by a read-only reviewer that built the slice in a clone, then built,
reviewed by a fresh reviewer and given one fix round: 1, the checklist (part 1); 3, property and differential tests
(part 3, beside slice 1); 2, rules from the merge base, REVIEW.md and `RULES` (part 2, on slice 1's merge); R, geppetto
roster 6, merged last with the installed copies. What the plan checks and reviews found is in
[things-that-bit/batch-18.md](things-that-bit/batch-18.md).

Left for later:
- A glob with non-adjacent repeated `**/` (`**/*/**/*/**/*/**/*/y`) is still slow on a long path. Repeated adjacent
  `**/` is collapsed now. It was already true of `riskyPaths` before Q24; the input is contrived.
- `RULES` sees only paths written in a `checks` command or a checklist `check`, as whole pieces. A check reached through
  another file (a Makefile, a `package.json` script) is not followed; TRIAGE.md says to name that file in `riskyPaths`
  or `checks`.
- A REVIEW.md that is a symlink at the base prints its target; the docs say to commit it as a regular file.
- `review-scope.mjs` (19,539 bytes) and `review-scope-rules.mjs` (19,733) are near the 20,000-byte limit: the next
  addition to either needs a split.
