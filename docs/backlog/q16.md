# Q16 trigger tests and a skill usage log

[Back to the backlog index](../BACKLOG.md)

**Q16 trigger tests and a skill usage log** (`in progress`, scope settled in decision 18). The owner asked for a new
capability and, a month on, two things: proof that the skills change what an agent does, and fewer misfires (the
right skill starts for the right request, and a wrong one does not). A brainstorm on 2026-10-26 weighed eleven
options; the owner chose these two together, and an interview settled the rest.

Two facts from the brainstorm, each from a one-turn headless run in an empty folder (8 US cents each):
- A run with `-p "<request>" --max-turns 1 --output-format stream-json --verbose` shows the skill the agent starts
  as a `Skill` tool call (`{"skill":"<plugin>:<name>"}`), then ends with `error_max_turns`.
- A `PreToolUse` hook with matcher `Skill` receives `tool_name: "Skill"` and `tool_input.skill`. A typed `/name`
  does not go through the Skill tool: it reaches only `UserPromptSubmit`, as the prompt text.

## Part 1: a trigger mode in skill-eval

- A new command in `skill-eval`, for anyone's skills: given a folder of skills, a folder of request lists, a model,
  a number of repeats and a cost cap, it runs each request as a one-turn headless `claude -p` and records the first
  skill started, or "none". It reports per skill: hits (a request that should start it did), misses, and misfires (a
  request that started another skill), and flags each request whose repeats disagree.
- Each run uses an empty HOME, only the project's settings and no MCP server, the way `skill-eval run` does, and sees
  only the skills under test; an `--also <folder>` flag adds other skills to test against.
- It prints its estimate before the first run and stops before it passes the cap. A summary goes to a file; given the
  previous summary, it prints what got better or worse.
- `skill-eval`'s SKILL.md is 17,043 bytes, so the mode goes in a new script and a new reference file next to it, with
  a short section in SKILL.md. `skill-eval` is already on the confirm list.

## Part 2: this repository's request lists and the first baseline

- `evals/triggers/<skill>.json`, one per skill, outside the skill folders, so the zips do not change. Each holds 3
  requests that should start the skill (one phrase from its description, one paraphrase that is not in it, one
  situation in plain words) and 2 near misses, each naming the skill, or "none", that should start instead.
- An agent that never sees the descriptions writes the paraphrases and situations, from each skill's body and the
  README's problem lists, so it cannot copy their wording. The orchestrator checks every list before the paid round.
- `npm test` checks the lists' shape: one per skill, 3 and 2 requests, every named skill exists. CI has no model, so
  the paid run is never part of it.
- The first full round: 38 skills, 190 requests, 2 repeats, 380 runs, about 30 US dollars with a cap of 40, on the
  model the session runs, priced to the owner before it starts. Its summary is committed in `evals/triggers/` as the
  baseline.
- This batch measures only. Rewriting the descriptions that misfire is a follow-up item, with the numbers in hand.

## Part 3: the skill-usage hook and the report

- A new hook, `skill-usage`, in `hooks/session-discipline/`, on by default and off through the hook config or
  `PAU_SKILLS_DISABLE`, like every hook here. `PreToolUse` with matcher `Skill` records a skill the agent started;
  `UserPromptSubmit` records a typed `/name` that names a skill.
- One line per start: the time, the skill name and how it started (typed or by the agent). Never the prompt, the
  folder or the session. It writes to a file under `~/.claude/pau-skills/`, outside every repository, trims the file
  when it passes about 1 MB, and exits 0 on anything it does not understand.
- `which-skill` gets a report script in its own folder: starts per skill, typed and by the agent, and the skills that
  never started in the last 30 days, for "which skills do I actually use?". Without the log it says how to switch
  the hook on. It works on its own, with only the skill uploaded.

## Changed in the orchestrator's review before the build (2026-10-29), and why

Checked against the code at 07045b5 and Claude Code 2.1.312.
- **The lists go in `evals/triggers/requests/<skill>.json`**, and the baseline in `evals/triggers/baseline.json` with a
  short `baseline.md`. The folder the mode reads then holds only lists, and the shape test can say "one file per
  skill" without exceptions. Format: `{ "skill": "<name>", "should": [3 requests], "nearMisses": [{ "request": "...",
  "expect": "<skill> or none" }, 2 of them] }`. The mode accepts any number of each; the repository test asks for 3
  and 2.
- **The writer never sees a description, so request 1 is not its job.** The orchestrator gives it a folder with every
  skill's body (frontmatter removed), the README's "Problems this fixes" sections, and for each skill the one phrase
  quoted after "Use when" in its description, which becomes request 1. The test fails when request 2 or 3, or a near
  miss, contains any phrase quoted in that skill's description, which catches copied wording.
- **A run sees every skill under test in its project's `.claude/skills/`**, not under the empty HOME:
  `--setting-sources project` hides skills under HOME (batch 8). A project skill comes back as `{"skill":"<name>"}`,
  a plugin or uploaded one as `<prefix>:<name>`; the mode and the report compare the part after the last colon. A
  built-in skill (`verify`, `debug`, `code-review` and the rest) counts as "another skill" by name.
- **A miss records the first tool the run used.** In one turn the agent may look around first (`ls`, a Read) and
  would have started the skill in turn 2. The summary tells "answered or did nothing" apart from "looked first", so
  the baseline shows how much the one-turn limit costs.
- **Counting**, per skill: hits (its own requests that started it), misses (its own requests that started nothing or
  another skill, named), and wrong starts (requests meant for another skill or for none, near misses included, that
  started it). A near miss is right when the named skill, or nothing, started. A request whose repeats differ is
  flagged unsteady.
- **Money as whole micro-dollars** (production rule 1, as in Q14). The estimate is runs x a price per run
  (`--usd-per-run`, default 0.08 from the brainstorm), printed before the first run; a `--plan` flag prints the
  count and the estimate and spends nothing. During the round the mode uses the highest real cost seen so far, never
  starts a run when what is spent plus the runs in flight plus the next could pass the cap, and passes
  `--max-budget-usd` to each run as a hard stop. Parallel runs default to a small number (rate limits).
- **The hook log** is one line per start, tab-separated: the time, the name as the tool gave it, and `agent` or
  `typed`. It lives under `PAU_SKILLS_HOME` or the home folder, as the hook config does, so tests never touch the real
  home. Past 1,000,000 bytes it keeps the newest half, written to a temporary file and renamed.
- **A typed `/name` is recorded only when it names a skill**: a `SKILL.md` for the bare name under
  `~/.claude/skills/`, `~/.claude/skills/synced/*/` or the project's `.claude/skills/` (or a plugin skill, if the plan
  check finds a cheap way to tell). A built-in or custom command is not a skill and is not recorded. The hook returns
  at once for a prompt that does not start with `/`, since it runs on every prompt.
- **The report** lists "never started in the last 30 days" from the same folders and says which ones it read; a skill
  that exists only inside a plugin cannot be listed there, and it says so.
- **Room left**: `which-skill`'s SKILL.md is 17,997 bytes and `skill-eval`'s 17,043, so each new section stays short
  (the 20,000-byte limit).
- **The baseline runs on the final descriptions**: after the integration, which may change the `skill-eval` and
  `which-skill` descriptions, and before the merge.
- **Fact checks need a small paid allowance**: a few one-turn runs, under 2 US dollars in all, to confirm on 2.1.312
  the Skill call of a project skill under an empty HOME and the hook inputs for an agent-started skill and a typed
  `/name`. Asked of the owner with the plan.

## Changed during the build (plan checks, reviews and fix rounds), and why

- `eng-lead` split the list part in two: B1 writes the lists blind, B2 writes the shape test, which reads the
  descriptions, from B1's commit. A fix round on the lists then stays blind.
- The B1 plan check found that the writer's input itself quotes 9 description phrases (`which-skill`'s router table,
  two bodies) and that `~/.claude/skills/synced/` holds every description. The writer may read only its brief, the
  standing orders and its input folder, may not reuse a quoted string from the bodies, and runs a hash-based overlap
  check that flags copied wording without showing it.
- The copied-wording rule matches whole words only, so "land it" does not match "island items".
- The A plan check found that the cap could be passed by the first parallel batch, that runs not made and failed runs
  were counted, and that a nonzero exit marked a normal one-turn run as failed. The review then found the cap still
  passable (1.76 of 1.00 US dollars) and a thrown run that lost the round. The final rule: the first run runs alone
  until a real cost is known; a run starts only when what is spent, plus the hard stops of the runs in flight, plus its
  own hard stop (twice the price) fits under the cap; the price is the highest real cost seen; a run that fails is one
  failed entry, and the round always writes its summary.
- The C plan check found that the tests could write to the real home, a trim test that never cut inside a line, a
  plain-object count that broke on `constructor`, and that linked skill folders were missed. The review found a crash
  on an unreadable log and four untested boundaries; all were fixed test first.
- The typed-name lookup also reads the synced plugin folder (`~/.claude/plugins/synced/*/<prefix>/skills/<name>/`),
  so a typed `/design:ux-copy` counts.
- The B review, reading the lists with the descriptions in hand, found 7 ambiguous requests and 3 near misses that
  tested nothing; B1 rewrote all 10 blind before the paid round.
- `.claude-plugin/marketplace.json` passes 20,000 bytes after the rebuild (21,470); it keeps its own limit in
  `.claude/pau-skills.json`, set before this batch.
- Left as they are: two hooks trimming the log at the same moment can lose one line (rare, costs one count); four
  mutations of B2's description-format checks survive (they guard only this repository's own SKILL.md format, and the
  test file is at 19,463 bytes).
