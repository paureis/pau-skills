**Q8 production rules from day one** (`in progress`, eighth batch; after Q6; touches `project-setup`, `geppetto` from Q2 and `rule-to-hook`).
Kept in Q6's brainstorm as a separate item.
- What it does: prevent the common gaps instead of finding them later. `project-setup` offers a short set of
  production rules for CLAUDE.md, picked by the project's profile (money as integers, validate on the server,
  parameterized queries, never trust a client-sent user ID, secrets out of the code). `geppetto`'s covenant for
  coding agents carries the same rules. `rule-to-hook` offers to enforce the mechanical ones.
- One source: the rules come from Q6's area files, so what is prevented and what is checked cannot drift. Each skill
  must still work on its own, so the rules a skill needs are copied into its folder and added to `COPIES` in
  `tests/standalone.test.mjs`, which keeps the copies identical.
- Done when: on a fixture project, `project-setup` offers rules that match its profile and leaves out the rest; Q6's
  audit of a project set up this way finds none of the gaps the rules cover; the copies pass the standalone test.
- Changed in the eighth batch's review (2026-10-23), and why:
  - One source file, `skills/verification/launch-readiness/PRODUCTION-RULES.md`, written for this item rather than
    generated from the area files: five rules between two marker lines, each a condition and an instruction so the
    block is safe in any project, then tables of the signals per rule and ecosystem, the check ids each prevents, and
    the checkers per ecosystem. A test fails when a cited id has no heading in the area files, so what is prevented and
    what is checked cannot drift. Identical copies in `project-setup`, `rule-to-hook` and `geppetto`, in `COPIES`.
  - Ownership is folded into the client-sent user ID rule, because ACC-01 is the gap agents leave most often.
  - In `geppetto` the rules are a second block, not part of the covenant: `builder` follows it and `reviewer` reports a
    break of one; `eng-lead`, `writer`, `sweeper` and the designer do not carry it. The audit checks the block only when
    present and at the bundle's roster version. The roster went to version 3.
- Changed during the build (plan checks, reviews and cold run), and why:
  - The plan checks corrected the rules: a publishable key such as a Stripe `pk_` key is not a secret (SEC-01 says
    so); "never a fractional amount in a binary float" (integer cents in a JavaScript number are fine); no request
    object passed straight in as a query filter; the user comes from the session, never from a value the client sets
    (a bearer token arrives in a header); the server decides owner, organization and role; secrets come from the
    environment the code runs in (a CLI has no server); JavaScript queries are checked with Semgrep or CodeQL, since
    eslint-plugin-sql does not see concatenation. Rule 5's signal is "any source file, or a goal that names an
    outside service, an API or a key", not "always", so an empty folder skips the question.
  - `project-setup` asks the new Q8 on the full path only; the quick path lists the matching rules as defaults, and a
    yes to that summary counts as choosing them. With one matching rule the options are "Add it" and "None". The old
    Q8 to Q12 are Q9 to Q13, and a test keeps the ids, the references and the quick list in step. The question count
    is worked out before the first question. Each chosen rule is one bullet of short sentences that keeps every
    instruction: the cold run's one-line form dropped the role check and the mass-assignment clause.
  - Rule 2's table says a bad body gets the framework's error (400, or 422 in FastAPI and Laravel).
  - `rule-to-hook` takes a production rule's examples from the rule's own text and the checker's documented cases,
    since it does not bundle the area files, and enforces one rule per run.
  - Cold run (claude-opus-5-5, empty HOME, the project-setup eval harness): on the web fixture the setup offered
    exactly Money, Input, The signed-in user and Secrets, each with a reason from the code, and not Queries (an
    in-memory store); on the Python CLI only Secrets. The grader's checks passed in every run. Then a refund feature was
    built twice on the web fixture: with the rules, amounts became integer cents end to end (the old float orders
    were fixed too); without them, refunds were stored as float dollars (COR-01 fails in the new code). Both took the
    user from the session, checked the owner and the reason length. Both kept an older gap: a catalog lookup by a key
    such as `constructor` gives a NaN total, and the refund route then accepts any amount.
  - Found and left for the owner: in every cold run and in one-turn runs at the base commit, `project-setup` read the
    project and opened with findings instead of its introduction. Stronger wording did not change it (0 of 3); telling
    it to send the introduction alone, ask "Shall I start?" and end its turn did (3 of 3).
