# Q43 the roster lock checks a change against main

[Back to the backlog index](../BACKLOG.md)

**Q43 the roster lock checks a change against main** (`done` 2026-11-27, pull request 108; found 2026-11-27 in the Q41 review). The roster lock
from Q41 fails a roster change with no bump, but someone who edits a roster file and rewrites `LOCK` with the new hash
under the same number passes every test. Only a reviewer reading the diff catches it.

Possible fix: a check that reads `LOCK` at the merge base (`git show <base>:tests/geppetto-roster-lock.test.mjs`)
and fails when the hash changed and the number did not, run in CI on pull requests and by `npm test` when a base is
known. It must pass when no base is reachable (a shallow clone, a fresh checkout) and say so.

Done when that check fails on a same-number `LOCK` rewrite (mutate.sh) and passes on the current tree.

Built in the twenty-eighth batch as `tests/geppetto-roster-lock-base.test.mjs`. It reads `LOCK` at a base commit and
fails when the hash changed and the number did not go up, or when the number went down. The base is
`ROSTER_LOCK_BASE`, else the merge base of HEAD and `refs/remotes/origin/main`; it never fetches. With no base it
passes with a `t.diagnostic` note saying why. CI checks out the full history and sets the base to `HEAD^1` on a pull
request (the base branch tip of the merge ref) and to `github.event.before` on a push (the previous main, which also
covers rebase merges and multi-commit pushes). In pull request 108 all four test jobs named base `HEAD^1` at main,
and the push run after the merge named `github.event.before`, the previous main.
What was left: in CI a no-base outcome passed with only a log line (fixed in Q44: it now fails), and only the end points are compared, so a
later rewrite under an already raised number passes (by design).
