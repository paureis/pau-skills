## What it is

Claude Ship takes a GitHub pull request through review, fixes and an approval decision. It has three parts:
- **Code Review** (generally available): reviews a PR through several lenses, verifies its findings and posts them.
  Levels Quick, Standard and Deep per repository. It reads `REVIEW.md` and `CLAUDE.md`, and reads `REVIEW.md` from the
  base branch, never from the PR's own changes. The local `/code-review` runs on any plan.
- **PR Steward** (beta): works on failing checks, merge conflicts and review comments, pushes fixes and comments with
  how to undo each one. It never approves or merges. `@claude` steers it, `@claude stop` stops it. A repository can
  give it instructions in `.claude/skills/steward/SKILL.md` (which checks matter, how to run the tests).
- **Claude Approvals** (beta): applies a policy in `.claude/approvals.yml` on the default branch (YAML, `version: 1`,
  `rules`, `mode: observe` or `enforce`), approving routine changes or asking for people. Observe mode only reports
  what it would decide, and its reviews are still billed.

`/ship` in Claude Code (v2.1.330 or later, `gh` 2.63 or later signed in, git 2.38 or later) commits, pushes, opens the
PR as you, runs `/code-review` on it, then watches it from your session and fixes failing checks and comments. It never
merges: "merge it yourself". It asks for no confirmation (an `Esc to cancel` line shows before the push). During an
unattended watch Claude Code blocks merging, approving, auto-merge and force pushes. The docs say `/ship` runs only in
the terminal and not in cloud sessions; the announcement says the desktop app too. `/autofix-pr` is the cloud
alternative.

Plans: Claude Ship, PR Steward and Claude Approvals are for Team and Enterprise only, and not with Zero Data Retention,
HIPAA or customer-managed keys. `/ship` bills your own usage; the docs do not say whether Pro or Max can run it.

## How it meets what we have

- **Our hooks.** No conflict found. `/ship` never runs `gh pr merge`, so `merge-guard` and `safe-merge` stay the way
  to merge. The `gh` and `git` commands Claude Code runs itself during a watch skip `PreToolUse` hooks and git hooks
  (`core.hooksPath=/dev/null`), so `no-verify-guard` and `destructive-guard` neither see nor block them. Fixes Claude
  makes with Edit and Bash during a watch still pass our hooks, and `verify-before-done` still applies to them.
- **REVIEW.md.** Q24 gave our `review-triage` and `lean-subagent-dev` a per-folder `REVIEW.md`, read from the base
  commit: the same name and the same rule as Code Review. A REVIEW.md written for one is likely read by the other.
  Check first: `skills/planning/lazy-senior/REVIEW.md` is the lazy-senior review mode, not review rules for that
  folder, and Code Review might read it as such (the customize page will say whether Code Review reads REVIEW.md in
  subfolders).
- **The batch flow.** Our orchestrator pushes, opens the PR, watches CI, sends fix rounds and merges with
  `safe-merge`. `/ship` does the push, PR, review and CI fixes for one change, but the batches run in cloud sessions,
  where `/ship` does not run.

## Results (pull request 80)

- Option 1: `lean-subagent-dev` and `safe-merge` name `/ship`. The user runs it on their own machine; an agent cannot
  start it (it "doesn't start from `claude -p` or from a program"). It may push fixes after the orchestrator's check
  and never merges, so the orchestrator reads what it pushed and reruns the checks at the new head before the merge,
  and `safe-merge` says to leave GitHub auto-merge off, since a fix `/ship` pushes could then merge the PR.
- Option 3 needed nothing. `code-review-customize` and `code-review-local` (read 2026-11-24) say only the managed Code
  Review reads `REVIEW.md` (Team and Enterprise; a subfolder `REVIEW.md` only on a protected branch, and it would
  then read `skills/planning/lazy-senior/REVIEW.md` as rules for that folder), while the local `/code-review`, which
  `/ship` runs and every plan has, reads `CLAUDE.md` only. Revisit if the owner moves to a Team plan.
- Also from `ship-command-troubleshooting`: in a public repository such as this one `/ship` commits nothing for you,
  and it does not start where a project hook could approve commands (ours never approve). The owner could not see
  `/ship` yet on 2026-11-24 (version, rollout or plan).
